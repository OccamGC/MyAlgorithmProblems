# 双语题面格式（草案 v0.1）

适用于每题的 `statement.zh.md` 与 `statement.en.md`。两份文件采用相同的章节顺序、数学符号、变量名、样例输入输出与约束；自然语言分别以中文和英文完整表达。

## 章节顺序

1. **标题和限制**：标题、参考环境下的预估时间限制、实际时限计算规则、内存限制。预估秒数供读者参考；实际时限由标准程序在目标评测环境的实测时间乘以约定倍率确定。内存限制暂沿用原题数值，后续单独讨论。
2. **背景故事**：简短的虚构情境，自然引出任务。可以保留本题原有故事的主要情节并替换敏感元素，也可以重新创作；不借用第三方题目的情节，不带入可识别个人、未发表故事专有名词或真实历史政治背景。若由 Codex 重新生成且未保留原有主要情节，在本节末尾标注实际模型名称。
3. **形式化问题描述**：独立定义对象、下标、操作、合法条件、目标和答案含义。读者跳过背景故事也应能准确解题。影响答案的规则只在这里或其后明确列出，不藏在故事中。
4. **输入格式**：逐行说明输入顺序、每个量的类型与含义；如果有多组数据，说明组数和终止条件。
5. **输出格式**：逐行说明需要输出什么，以及多解、精度或特殊评测要求（如适用）。
6. **样例**：每组样例分别放在 `text` 代码块中，两个语种的输入输出字节一致，并与 `tests/samples/` 的文件对应。
7. **样例解释**：只解释有助于理解规则或答案的步骤；没有必要时可写简短说明，不引入新规则。
8. **数据范围与保证**：先列适用于 **100% 数据** 的通用范围与保证。正式数据确有分组时，再列各组的额外条件；没有额外条件的组直接写“无额外条件”。各组比例应合计 100%，且生成计划须落实这些比例；未落实前在内部记录中标为待核实，不在正式题面宣称。不要凭空添加更严的限制。

## 写作约定

- 背景中的角色和物品与形式化对象有清楚对应关系，但形式化部分应使用稳定的术语和记号。中文与英文可采用自然的不同句式，不能改变规则。
- 重写故事的署名放在背景故事最后一行，例如中文版 `(本故事由GPT-6 Sol重写)`、英文版 `(This story was rewritten by GPT-6 Sol.)`；两版模型名称一致。保留原有主要情节时无需署名，局部修改不改变这一判定。
- 经确认加强数据范围的题目，在“数据范围与保证”中注明加强者及实际模型，并说明范围的变化；例如“本题数据范围由 Codex（GPT-6）加强”。算法名称和具体解法贡献放在题解与标程署名中，不在题面署名里提示解法。规则见[数据加强与解法署名](翻新工作流草案.md#已确定的方向)。
- 题目要求应明确是求值、判定、计数还是构造；输出格式和评测方式与此一致。
- 所有边界约定（例如空集、无解、是否允许重边）放在形式化描述或数据范围中，不能只从样例推断。
- 分组表采用“分值比例 / 额外条件”两列。所有组都必须满足通用范围；`tests/plan.json` 中每组测试文件的 `score_percent` 之和须与题面对应。不在题面中解释条件来自旧版或仍待核实。Markdown 表格内的绝对值符号用 `\lvert T\rvert` 等写法，避免 `|T|` 被解析成列分隔符。中英文表格的比例、条件和顺序应对应。
- 时间限制按[性能约束方案草案](性能约束方案草案.md)与题库级参考环境配置给出；不得把原题秒数直接当作参考环境下的预估值。单题记录应注明实测结果、倍率和仍需复测的疑点。内存限制暂保留原题数值与单位。
- 背景故事与形式化问题描述是每题的固定章节；即使是纯数学题，也先尝试用极短的原创情境引出问题。若原题有子任务、交互协议、输出精度等特殊要求，增加对应章节；无此要求时不放空标题。

## 游戏背景与图片

背景可以保留知名游戏中的虚构人物、剧情和物品；真实历史事件及明确要求替换的隐私、未发表故事内容仍需改写。私人游戏服务器的村镇、部门、组织等特定名称改为相似但不同的虚构名称，不按知名游戏的官方设定保留；中英文使用一致的替代名称。

图片按[工作流中的图片与示意图规则](翻新工作流草案.md#图片与示意图)处理：移除无关展示图；用于解释题意的图例核对后重新绘制，保存到题目内的 `assets/`，再用 Markdown 图片语法嵌入，例如 `![解释图片内容的替代文本](assets/movement.svg)`。优先 SVG，需要兼容其他阅读器时可另导出 PNG。

坐标网格、作用范围、移动规则和样例路径等均采用实际图片，文字与表格不能替代这些图例。图应放在相关规则或样例解释旁，配有简短图注，正文仍完整定义规则。数据范围、评分分组等表格照常保留。

两种语言的图片内容必须一致，可共用带通用符号的图片并分别写替代文本和图注；自然语言标签较多时制作对应的中英文图片。图片必须实际渲染检查，不能只检查 SVG 源码或文件是否存在。

## 变量命名与公式释义

本节同时适用于中英文题面与题解。翻新时可以根据含义和阅读习惯，更换表示数据的字母、缩写或记号；优先选择清楚、常见且容易区分的写法，不要求沿用原有命名。

- **按含义选记号**：数量、下标等可使用常见的单字母；业务含义较强的量可使用有意义的缩写或全称。同一道题中避免一个符号表示多个不同的量，也避免仅靠容易混淆的大小写区分关键概念。
- **首次出现时说明含义**：例如“生命值 $H$（Health）”或“生命值 $\mathrm{HP}$（Health Points）”。简称和全称能减轻记忆负担时，可以同时给出；含义明确的常见符号不必强行扩写。符号较多时，可用简短的“符号 / 含义 / 单位或范围”表集中说明。
- **按需要补充全称公式**：涉及多个业务量、符号不易记忆或运算含义不直观时，可在关键符号公式旁补一份使用完整名称的公式，或一句等价的文字解释。题面用于解释任务和规则；题解用于解释算法状态和推导。无需将每一步推导都重复两遍，也不把仅属于题解的结论提前写入题面。
- **两种公式必须严格等价**：全称版保留正负号、上下标、求和范围、取整、条件和边界约定。长公式可拆行或分步解释，避免为了写出全称而降低可读性。多字母缩写使用 `\mathrm{HP}` 等写法，完整文字名称使用 `\text{...}`，避免被读成多个变量相乘。
- **同步相关材料**：符号调整后，核对中英文题面、题解、输入说明、数据范围、样例解释、图示、标准程序和生成器中的对应记号与说明。两种语言采用同一套符号，完整名称按各自语言自然表达。代码可使用更具描述性的英文标识符，但必须能明确对应到题面变量，并遵循 C++ 命名规范。
- **区分改名与改规则**：单纯更换记号不改变数量含义、单位、下标范围、输入顺序或数据语义。在内部翻新记录中保留必要的旧记号到新记号对应关系；若同时修改规则，单独记录并验证。

例如，已说明 $H$ 为回合开始时的生命值、$H'$ 为回合结束时的生命值、$A$ 为存活敌人的攻击力总和后，可给出符号公式：

$$H'=H-A$$

需要帮助读者联系含义时，再补全称版本：

$$\text{回合结束生命值}=\text{回合开始生命值}-\text{存活敌人攻击力总和}$$

如攻击力允许为负，正文仍需说明负攻击力表示回复生命；全称公式不替代这项规则。

## 复杂度中的参数

本节同时适用于中英文题解。

- 复杂度依赖二进制位数、数值上界、字符集大小等量时，用含义明确的符号表示，或写成对数值上界取对数等对应表达式；不要把由本题约束得到的具体数值直接代入复杂度公式。
- 首次使用参数时说明含义及其与题目约束的关系。例如，非负整数的上界为 $U$ 时，可定义二进制位数 $B=\max\{1,\lceil\log_2(U+1)\rceil\}$ ；涉及数值为零或上界恰为二的整数次幂时，须正确处理位数边界。
- 推导、求和范围与复杂度使用同一套参数。具体取值放在实现说明中，例如说明本题 $U=65536$ 、$B=17$ ，复杂度仍写为建树 $O(nB)$ 、每次操作 $O(B\log n)$ 、空间 $O(nB)$ .
- 中英文同步定义参数，并分别写清时间、空间复杂度。普通常数因子按大 O 记号的惯例省略，无需为固定的几次基本操作另设符号。

## 数学记号与标点间距

本节同时适用于中英文题面与题解。

- 正文中的变量、单个字母和数学表达式统一使用行内公式；程序标识符和字面字符使用行内代码。
- 公式中的 LaTeX 命令必须保留反斜杠，例如 `$n,m\ge1$`、`$nm\le1000$`、`$tp\in\{0,1\}$` 和 `$0,\ldots,p-1$`。需要显示的集合花括号写成 `\{`、`\}`；普通 `{...}` 只用于公式分组。正斜杠 `/` 不能代替命令前的反斜杠 `\`。
- 程序生成 Markdown 时须正确处理字符串转义，例如 Python 使用原始字符串 `r"$n\ge1$"`，确保最终 `.md` 中命令前保留一个反斜杠。编辑或格式化后运行 `tools/check_statements.py`，对照双语题面和题解中的行内、独立公式，检查命令或集合括号是否丢失转义；不能仅检查独立公式。
- 行内公式或行内代码后紧接逗号、句号、顿号、分号、冒号、问号或感叹号时，在两者之间直接插入一个 Unicode 不换行空格（`U+00A0`），文件以 UTF-8 保存。例如源码写作 `$a_i$ ，`、`$n$ .` 或 `` `PrintPrefix(t)` ：``。若公式带有加粗或斜体，将间隔放在强调标记之后。
- 字母、公式或行内代码后紧随的句号统一使用英文句号 `.`，中文题面和题解也遵循此规则；普通中文文字结尾仍使用中文句号 `。`。
- 不写成 HTML 实体 `&nbsp;` 或 `&#160;`，以免编辑器的实时预览直接显示实体源码。上面的示例包含实际的 U+00A0 字符，可直接复制；程序生成文档时可用 Python 字符串 `"\u00a0"`，写入的是字符本身，不能把字面量 `\u00a0` 写进正文。
- U+00A0 在编辑时与普通空格外观相近；批量整理空白时必须保留这些字符。
- 不使用普通空格代替：不换行空格既保留间隔，也避免标点单独换行。
- 仅分隔正文标点；公式内部的参数逗号、小数点、集合及区间记号保持其数学含义。独立成行的公式不在公式末尾附加句子用的逗号或句号，内部的数学标点仍保留。
- 样例输入输出、代码块和实际数据中不插入排版空格；普通自然语言单词与标点仍按各语言习惯书写。

## 尚待讨论

1. 时间取整粒度已确定为 0.5 秒，倍率默认 `2` 且可逐题调整；内存限制的后续处理方式仍待讨论。
2. 背景故事的推荐篇幅，以及极抽象题目如何避免生硬的故事。
3. 样例是否由文件自动同步到 Markdown，还是先通过人工或脚本核对。
4. 多组数据、子任务、交互题和特殊评测题的统一章节细节。
