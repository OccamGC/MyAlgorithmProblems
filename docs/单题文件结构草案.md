# 单题文件结构（草案 v0.2）

目标：一个题目目录即可阅读题目、理解解法、编译参考程序，并按固定配方重新生成测试数据。原仓库只读；此处只存放翻新成果。

已确认的技术约定：以 Python 3 标准库作为测试数据生成与运行入口；参考程序和需要高性能的生成器默认使用标准 C++17，使用者自行编译源码。C++ 源码遵循[项目编码风格规范](C++编码风格规范.md)。Python 的最低小版本和具体命令行接口在试运行时确定。

## 推荐目录

```text
topics/<topic>/<problem-slug>/
├── statement.zh.md       # 中文题面
├── statement.en.md       # 英文题面
├── solution.zh.md        # 中文题解
├── solution.en.md        # 英文题解
├── std.cpp               # 参考程序源码
└── tests/
    ├── samples/          # 仅提交体积小、需要随题面展示的样例
    │   ├── 01.in
    │   └── 01.out
    ├── plan.json          # 测试组、分值、参数、固定种子和设计目的
    └── generate.py        # 根据 plan.json 生成正式测试数据
```

按需添加以下文件，不建立空目录：

```text
<problem-slug>/
├── assets/               # 重绘的解释性图例（优先 SVG，按需附 PNG 或生成脚本）
├── checker-utils.hpp     # 评测器或辅助程序的公共实现，不作为 std.cpp 的依赖
├── brute.cpp             # 可对拍的独立小规模解法
├── alternative.cpp       # 补充方案源码；首选、并列或备用地位及适用范围见题解
├── solution-alternative.zh.md # 补充方案中文题解
├── solution-alternative.en.md # 补充方案英文题解
└── tests/
    ├── manual/           # 少量难以生成的手工边界用例
    ├── validate.py       # 输入合法性检查
    ├── generator.cpp     # Python 生成数据过慢时使用的生成器源码
    └── checker.cpp       # 非唯一输出等特殊评测所需源码
```

`<topic>` 与 `<problem-slug>` 使用稳定的小写 ASCII 名称，单词之间用连字符，避免不同系统的大小写和文件名规则冲突。中文和英文标题写在题面里，不依赖目录名表达。主题组可包含任意数量的题目；跨主题归属与标签规则另议。

按[补充解法规则](翻新工作流草案.md#补充解法与计算程序)交付每种符合条件的解法及其计算程序。只有一种补充方案时可以使用上面的 `alternative.cpp` 与双语题解文件名；有多种时使用 `alternative-<method>.cpp`、`solution-alternative-<method>.zh.md` 和 `solution-alternative-<method>.en.md`，其中 `<method>` 为稳定的小写 ASCII 方法名。已有文件名可以保留。首选题解须链接各方案及源码，共同推导可以放在首选题解中复用；每种方案仍须有完整说明和对应的可运行程序。

题目另按[五类状态](题目状态分类.md)记录材料齐备程度与检验结果；状态不体现在目录层级中，因此复核或修复后不必移动题目文件。

题面的章节设计见[双语题面格式草案](题面格式草案.md)；对应的中文与英文文件已放入 `templates/problem/`，题解格式仍待讨论。

## 数据与可复现性

- 版本管理中保留源码、四份 Markdown、题面引用的重绘图例、小样例、必要的少量手工用例、生成计划和生成器。图例与题面一并维护；需要生成脚本时也保留脚本。正式大数据写入题目目录以外的本地构建目录，例如仓库根目录的 `build/data/<problem-slug>/`，并忽略该目录。这也符合 [GitHub 对程序生成文件的仓库体积建议](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)。
- `plan.json` 记录每组测试的编号、所属分组、分值比例、范围或形状、随机种子及目的；各组分值与题面一致。`generate.py` 接收计划和输出目录参数。相同版本的生成器与计划应生成相同输入。若随机库或运行时版本会影响结果，要固定版本或使用明确实现的伪随机算法。
- 生成逻辑产生输入。标准输出由使用者自行编译 `std.cpp` 后批量运行得到；`generate.py` 通过参数接收参考程序的可执行文件路径并写出输出文件。若生成输入需要 C++，使用者也自行编译 `generator.cpp` 并把其路径传给脚本。仓库不保存可执行文件。非唯一输出的题目按其评测方式处理。
- 样例数据可以同时出现在 Markdown 和 `tests/samples/`，但必须在复核时比对一致。若试运行发现重复维护容易出错，再改为自动嵌入或校验。
- 大小阈值暂不写死：原则上不提交可由生成器重建的大数据，单个确需提交的大文件需逐题说明原因。
- `docs/` 保留维护规范、公开技术分析和题解引用的测量记录；输入、源码哈希与逐次计时是复现依据，可以提交。批次进度、原题路径、改写过程、一次性修改脚本和本机操作记录放入已忽略的 `review/` 或 `build/`。提交前同时检查已跟踪文件和未跟踪文件，不能只依靠 `.gitignore`；小样例的 `.in`、`.out` 不应被通配规则忽略。

## 跨平台约定

- 交付源码、文本与通用图片格式，不打包 Windows、Linux 或 macOS 可执行文件，也不依赖平台专属的构建产物。
- 参考程序和可选的 C++ 生成器使用标准 C++17；生成脚本使用 Python 3 标准库。个别题目确需其他语言、库或编译选项时，在题目记录中明确写出。
- C++ 代码采用 UE C++ 风格的大驼峰命名、另起一行的大括号和制表符缩进；可为对应题面符号保留 `n`、`m` 等特殊大小写。完整规则见[编码风格规范](C++编码风格规范.md)，不使用 UE 头文件或引擎依赖。
- 生成脚本使用 `pathlib`、命令行参数和标准库文件操作，避免硬编码盘符、路径分隔符、Shell 命令及平台专属 API。输入输出文件统一为 UTF-8 文本和 LF 换行。
- `std.cpp` 必须包含完整的标准解法，可单文件独立编译或直接提交，只依赖标准库头文件，不依赖自定义 `.hpp`、其他源码文件或外部生成代码。辅助程序可复用标程函数，但不能反过来成为标程的编译依赖。验证时将 `std.cpp` 单独复制到隔离目录编译并运行样例。
- 使用者按本机编译器编译 `std.cpp`；生成脚本通过传入的可执行文件路径调用该程序。示例命令可以给出，但不把某个编译器或操作系统作为唯一方式。

## 与现有题目包规范的关系

此结构优先服务于源代码管理、双语阅读和本地再生成数据，暂不声称兼容任何 OJ 题目包格式。如果之后确定投放平台，再编写导出脚本或增加目标平台所需的文件，而不让每题维护多套源文件。[Kattis 题目包格式](https://github.com/Kattis/problem-package-format)及其[验证工具](https://github.com/Kattis/problemtools)可作为后续导出的参考。
