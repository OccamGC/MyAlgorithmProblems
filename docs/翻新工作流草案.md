# 原创题目翻新工作流（草案 v0.1）

> 这是一份试运行规则。原始题目仓库只读；所有翻新成果写入独立的翻新仓库。根据实际工作量和发现的问题修订流程。

## 目标与范围

让每道翻新后的题目具备可信的题面、题解、程序和测试说明，并能追溯它与原版的区别。翻新可以只修订文字，也可以改动约束、算法或数据；改动范围必须逐题记录。

本流程适用于从原仓库选出的正式题目。原仓库的 `ideas/`、`notes/`、放弃的题目等是否纳入，待试运行后决定。读取原题时记录其来源，不在原仓库中修改、移动或重命名文件。

## 已确定的方向

以下是翻新成果的要求；文件命名、目录层级和具体写法留待后续讨论。

1. **双语 Markdown**：每题的题面有中文、英文 `.md` 各一份；题解也有中文、英文 `.md` 各一份。两种语言描述同一份题意、约束、样例与算法，不把英文版当作简写。具体章节格式、术语和文件名待定。
2. **按主题分组**：新版题库以题目主题组织，不沿用“某某模拟赛”作为主目录。一组可以包含多道题。主题清单、交叉主题题目的归属方式待定。
3. **替换可识别个人的信息**：新版题目与题解中的真实姓名、网名、缩写及其组合，只要可能指向具体个人，就替换。无法识别具体个人的泛称（如“小W”）可以保留。原题中关联未发表故事的组织、国家、地名及其他专有名词也要替换。私人游戏服务器中的特定村镇、部门、组织等名称同样替换为相似但不同的虚构名称，中英文保持对应。不要把待替换名称的清单复制到新版题库。
4. **替换真实历史与政治内容**：新版题目中涉及真实历史或政治的名称、口号、事件背景等改为中性或虚构设定。知名游戏中的虚构剧情、人物、阵营和物品可以保留，不因名称具有历史或政治色彩而一律替换；直接叙述真实历史事件的部分仍需改写。此前明确要求替换的个人隐私、未发表故事专有内容及私人服务器设定不适用这一例外。替换后须复核题意及数据含义；如果背景与算法规则纠缠，先讨论如何改写。
5. **保留有趣且清楚的背景**：可参考历年 NOI / NOIP 题目的叙事方式，用简短的虚构故事自然引出计算任务。可以保留本题原有故事的主要情节并替换敏感元素，也可以重新创作背景；不照搬第三方竞赛题目的具体人物、情节或原文。必要的规则仍要用明确的数学或操作描述写清楚。
6. **源码交付与数据再生成**：新版题目采用[单题文件结构草案](单题文件结构草案.md)。默认以 Python 3 标准库组织数据生成，参考程序与高性能生成器使用标准 C++17。交付源码和生成配方，由使用者自行编译，不打包平台专属可执行文件或正式大数据。
   C++ 源码遵循[项目编码风格规范](C++编码风格规范.md)：参考 UE C++ 的大驼峰命名和换行大括号，允许与题面一致的 `n`、`m` 等数学符号；不依赖 UE 头文件。
7. **分层性能约束**：题面给出参考环境下的预估时间限制，并注明实际时限由标准程序在目标评测环境的实测时间乘以倍率确定。倍率默认 `2`，可逐题实测调整并记录原因。题目规模和保证独立于评测机；具体校准方法见[性能约束方案草案](性能约束方案草案.md)。
8. **五类题目状态**：按[题目状态分类](题目状态分类.md)记录每题的材料齐备程度与检验结果。题目目录仍按主题组织，状态变化不触发搬迁。
9. **重写故事署名**：若背景故事由 Codex 重新生成，且没有保留原有故事的主要情节，在故事末尾单独一行标注实际生成模型，例如 `(本故事由GPT-6 Sol重写)`；英文题面同步写 `(This story was rewritten by GPT-6 Sol.)`。若切换为 Astra 等其他模型，应写实际模型名称。保留主要原有情节时，即使替换或改写了部分内容，也不加此标记。判定与模型名称记录在内部翻新记录中。
10. **数据加强与解法署名**：经用户确认加强数据范围或设计加强版时，在中英文题面的“数据范围与保证”中注明由 Codex 及实际模型加强，并写清加强或重新设计的范围。由 Codex 在本次工作中改进或提出的解法，在双语题解开头及对应标程文件头注明贡献者和具体贡献。基于已有算法的应用、改进、证明与实现如实描述，引用所依赖的方法；署名指本题中的工作贡献，不将已有算法归为模型原创。数据与解法署名独立于故事署名，不能互相替代。
11. **保留出题人解法并说明取舍**：更换算法时，双语题解须保留出题人解法，并比较各方案的优势、代价与适用条件，明确首选、并列或备用地位。只有原解法存在根本性错误时，才可不将其作为有效解法，仍须给出错误原因或反例。发布文字直接介绍方案，不叙述新旧切换过程。具体要求见下节。
12. **使用发布口吻**：题面、题解、随题说明及公开目录只保留解题、实现、使用和评测所需的信息。署名写“出题人解法”与 Codex 的实际模型及贡献，不写出题人姓名；修改过程另记在内部记录中。具体要求见[发布文字与署名](#发布文字与署名)。
13. **主动补充优秀解法与计算程序**：逐题检查是否存在更好、更优雅的解法，或同等优秀但解决思路显著不同的解法；发现符合条件的方案时，须补充中英文解法说明及可编译运行的计算程序，并完成相应验证。具体要求见[补充解法与计算程序](#补充解法与计算程序)。

替换范围至少覆盖新版标题、背景、题面、题解、样例文字、图片说明及公开使用的文件路径；程序注释和生成器输出若会进入交付物，也要检查。原仓库及其 Git 历史保持原样。单题记录中的原题路径仅供内部追溯，不随题目对外发布。

## 原解法保留与改动说明

- 先对照原题解、标程及相关证明，确认原算法及其适用范围；多个版本须在内部记录中说明采用哪一版作为比较依据。材料不足时注明待核实，不凭新版代码反推原解法。
- 更换算法、数据结构或影响复杂度的实现策略时，在中英文题解中保留可独立理解的出题人解法：关键思路、操作过程、正确性依据及时间／空间复杂度。相同部分可以共用正文，用算法名称和署名区分各方案；无需重复整篇题解，也不要求另交一份原程序。哪些内容沿用或改变，在内部记录中追溯。
- 明确区分算法改进、另一种解法和同一算法的实现整理。优势须落实到可核实的复杂度、数值安全、边界处理、可移植性或代码组织；同时交代增加的开销和适用条件。未测量新旧程序时，不宣称运行速度或实际内存更优；同阶复杂度的替代方案不得笼统称为优化。
- 原解法本身正确，而程序存在溢出、空输入、递归过深、标记下传等可修复缺陷时，仍应保留原解法，并将实现问题与算法结论分开说明。
- “根本性错误”指建模、核心推理或必要假设不成立，使该解法不能正确解决题目。使用这一例外时，题解简述反例或错误推理，内部记录保存证据；不把已知错误方案当作有效解法。不能只因新版更方便实现而使用例外。
- 修改贡献署名时，对照原材料确认贡献范围，不将原程序已有的建模、数据结构或技巧归为 Codex 原创。复核已翻新题目时，同样补齐出题人解法、署名与方案比较。
- **标程与题解首选原算法**：原算法正确或仅需可修复的实现调整，而替代算法在时间、空间或适用范围上没有明确优势时，采用修复后的原算法作为 `std.cpp`，并将其作为双语题解的首选。代码较短、证明较统一或容器更熟悉，不能单独作为替换原算法的理由。同一算法的数值修复、显式遍历和编码整理可以保留，不必恢复旧程序缺陷。
- 已有替代方案保留为 `alternative.cpp` 与 `solution-alternative.zh.md`、`solution-alternative.en.md`；多个方案按[单题文件结构](单题文件结构草案.md)使用带方法名的文件名。由首选题解链接，并说明是否能通过当前完整数据。**时间更慢但有明确空间或其他优势的方案，与原解法并列介绍**，写清各自适用条件和当前标程选择依据；不得仅因速度较慢将其降为无优势备用，也不得悄悄删除任一方案。
- 对渐进时间更高的备用方案，先在同一编译环境下比较可复现压力数据。可通过扩大规模或缩短时限稳定区分时，同步更新双语范围、数据分组、生成器、校验器、测量及加强署名。时限仍按标准程序实测乘倍率后以 0.5 秒向上取整，并核对通过与超时余量。无法形成可靠间隔时如实记录，不为了卡某份实现而压缩正常通过余量，也不把一份程序超时当作排除全部同阶算法的证明。

## 补充解法与计算程序

- 翻新每道题时，主动检查更好的算法、更优雅的表达与实现，以及同等优秀但思路显著不同的方案。发现符合任一条件的有效解法，须将其补充到交付物中；不以原标程已经正确为由跳过。
- 说明补充价值及依据：更好可以体现为时间、空间、数值安全或适用范围的改善；更优雅可以体现为更自然的建模、更清晰的不变量、更简洁的证明或实现；同等优秀的不同思路应交代建模、核心推理或算法结构的实质区别。单纯改名、换容器或格式整理不作为独立解法；未实测时不宣称实际速度或内存更优。
- 每种补充解法均提供可独立理解的中英文说明，包括关键思路、正确性证明、时间／空间复杂度、适用条件及实现注意事项，并交付与说明对应的可编译运行程序，默认采用标准 C++17。共同推导可以共用正文，但不能只列算法名称、伪代码或外部链接而缺少计算程序；贡献与方法来源按既有署名规则说明。
- 在首选题解中链接全部补充方案与源码，比较各自优势、代价及适用条件，明确首选、并列或备用地位，以及能否通过当前完整数据。标程选择仍按[原解法保留与改动说明](#原解法保留与改动说明)执行；更优雅或同等优秀的不同思路可以作为补充方案，不必替换原标程。
- 对每份补充程序编译并检查样例、关键边界，用独立小规模解法对拍或给出适合该题的替代验证；对适用范围和性能结论提供对应证据。未完成证明或验证的候选方案留在内部待核实记录中，不能作为已完成的有效解法发布。
- 在单题记录中写明检查过的候选思路、是否补充及理由，并登记题解、程序和验证证据的位置。未发现符合条件的方案时如实记录检查结论，不为增加解法数量而勉强补充。

## 发布文字与署名

- 以读者需要的最终内容组织公开材料。删除“本次复核”“此前新版”“恢复原标程”“经确认后修改”“本批已完成”等工作过程说明，不以“原方法／新方法”切换作为题解主线。用具体算法名称、首选方案、并列方案或备用方案表达关系。
- 保留出题人解法的思路、证明、复杂度及必要的实现差异；保留其他方案的优势、代价、适用范围、程序和完整题解。删除过程叙述不等于删除算法依据，也不改变标程选择规则。
- 署名统一使用“出题人解法”（英文 “Problem setter’s solution”），不写出题人的真实姓名或网名。Codex 采用的算法、实现与证明贡献按实际范围署名，并保留实际模型。故事、数据加强与解法署名仍分别执行已有规则。
- 仅有实现缺陷时，将有用的修复结论改写成实现注意事项，例如“空序列不递归建树”“不存在合法换边时跳过候选”；错误发生在哪一版、如何发现和修复，留在内部记录。无效建模的反例仍应在题解中说明。
- 理论复杂度与实际运行表现的分析属于题解内容，应保留可复现数据、输入条件与测量局限。以算法名称比较，不使用“旧版／新版”；明确超出正式范围的实验规模，以及备用程序是否能通过当前完整数据。
- 题目链接优先指向发布用的评测环境、测量数据和使用说明。修改记录、批次进度、讨论过程及历史选择保留在内部维护材料，不作为题面或题解的默认阅读入口。中英文同步检查，避免将“原树”“旧标记”等算法术语误当成过程文字。

## 变量记号与全称说明

翻新时允许把表示数据的字母、缩写或记号替换为更合适的写法。可在首次出现时提供简称和全称，或用符号表说明含义；对容易误解的关键公式，视需要补充全称版公式或等价文字说明。中英两版及题解、代码、图示等材料须保持明确对应，符号变化与实质规则变化分别记录。具体要求见[变量命名与公式释义](题面格式草案.md#变量命名与公式释义)。

## 图片与示意图

- 删除对理解题目没有帮助的游戏单位展示图、阵营徽标、装饰图等。
- **解释题意的图例统一重新绘制，再嵌入 Markdown**：包括坐标、作用范围、图或树的结构、操作过程、移动规则及样例路径。先核对原图和新版题意，不直接复制旧图。简单网格和关系也绘制成实际图片，不再以文字、Markdown 表格、字符图或未渲染的 Mermaid 代替图例。
- 图片放在单题目录的 `assets/` 中，优先保存清晰、可编辑的 SVG；确有兼容性需要时另导出 PNG。用 Markdown 图片语法和相对路径嵌入题面或题解，图片紧邻对应说明，并提供有意义的替代文本、图例和简短图注。制作脚本可随资源保存，以便规则或符号变化后重新生成。
- 中英文使用一致的几何结构、数据和标记。优先在图内使用正文已解释的通用符号，共用同一张图；需要自然语言标签时分别制作中英文版本。坐标方向、下标、端点、包含或排除的边界必须与正文一致，不能只靠颜色区分含义，还应使用文字、符号、轮廓或纹理。
- 正文仍须独立、准确地定义规则，图例负责直观解释。分值、约束、数值对照等真正的数据表格可以保留；原本用于模拟空间布局或操作过程的表格应换成重绘图片。
- 盘点时逐题登记原有解释性图例及新版对应资源；已转换的题目也要回查有无遗漏，或是否被文字、表格替代。完成后实际渲染并查看所有重绘图，检查文字可读性、遮挡、裁切、箭头和边界，核对中英文引用及资源路径。

## 单题流程

### 1. 盘点

- 找齐原题面、备忘、题解、标程、暴力程序、数据生成器、特殊评测程序及现存数据，记录路径与缺失项。
- 提炼原解法及其证明、复杂度，记录依据的材料版本，为后续比较保留证据。
- 盘点题面和题解中的图片，区分解释性图例与装饰图；逐项记录需重绘、可删除及待核实的内容。
- 用几句话复述题目要解决的问题，列出题面、代码、数据之间明显矛盾或不确定的地方。
- 初步判断题目所属主题，标出需要替换的个人信息、未发表故事名词、真实历史和政治内容。记录中只写需处理的位置与处理状态，避免重复传播个人身份对应关系。
- 确定本次改动级别：**文字整理**、**技术修复**或**重新设计**。级别可以在验证后调整。
- 建立一份[单题翻新记录](单题翻新记录模板.md)，持续记录结论和证据。

### 2. 定稿题意与规格

- 明确输入、输出、约束、数据范围、评测方式和所有需要解释的边界情况。
- 将适用于所有数据的通用范围与仅适用于部分数据的分组额外条件分开写；核对分组比例之和，并在生成计划中落实。旧版来源及条件缺失等核查信息只写入内部记录，不放进新版题面；不能据此编造额外条件。
- 判断原解法与预期难度是否仍合适；如需更改算法要求或约束，在记录中说明原因。
- 将不确定的规则列为待决项，不凭代码行为直接推定题意。
- 为需要换背景的题目拟定原创故事梗概，检查故事中的对象和操作能否与原题规则逐一对应。
- 判断故事是保留原有主要情节还是由 Codex 重新生成；后者记录实际模型，并在中英文背景末尾加对应署名。
- 拟定中英两版题面和题解，核对标题、定义、约束、样例、算法步骤与复杂度在两种语言中一致。
- 检查数据记号是否易懂，必要时更换字母或补全称；为有理解障碍的关键公式提供等价的全称版或文字解释，并核对全部材料中的符号对应关系。
- 按[数学记号与标点间距约定](题面格式草案.md#数学记号与标点间距)，在行内公式或代码与紧随的正文标点之间直接插入一个 `U+00A0` 不换行空格（保存实际字符，不写 HTML 实体），紧随的句号统一使用英文句号 `.`；样例、代码和公式内部的数学标点不作此处理。
- 完成背景与名称替换，检查替换是否改变题意。新版文件只写入独立的翻新目录。

### 3. 整理实现与数据

- 确认至少一份参考解法与新版规格一致，并写明时间、空间复杂度及适用范围。按[复杂度中的参数约定](题面格式草案.md#复杂度中的参数)定义位数、值域大小等参数，避免将约束中的具体数值直接代入复杂度公式。
- 对照原解法，在双语题解中补齐出题人解法、署名、各方案的优势与代价；纯替代方案明确标注，使用根本性错误例外时给出依据。发布口吻按[发布文字与署名](#发布文字与署名)检查。
- 按[补充解法与计算程序](#补充解法与计算程序)检查候选方案；对符合条件的解法补齐双语说明与对应计算程序，在单题记录中登记检查结论。
- 按[项目 C++ 编码风格规范](C++编码风格规范.md)整理参考程序及其他 C++ 源码；纯格式整理与算法修复分别记录。
- 如有生成器、暴力程序或特殊评测程序，说明各自用途、运行方式与依赖。
- 补齐或调整样例、边界数据、针对错误做法的数据；记录生成方式与随机种子（如适用）。
- 原仓库忽略 `*.in`、`*.out`、`*.ans`；这些规则不会自动成为新版题库的规则。新版测试数据是纳入版本管理、通过脚本再生成，还是保存在外部位置，尚待确定。

### 4. 验证

- 人工复核题面：定义、格式、样例、解释和约束互相一致。
- 检查故事是否帮助理解任务，所有影响答案的规则是否写得明确；中英两版背景指向同一问题。
- 核对重写故事的中英文署名均位于背景末尾，模型名称一致；保留主要原有情节的故事不加署名。
- 对照中英两版题面和题解逐项复核；检查新版公开材料是否仍出现需替换的名称、缩写或背景。
- 对照原材料核实原解法没有遗漏或被误述，改动优势有证据，替代方案与实现修复标注准确，双语对照说明及贡献署名一致。
- 核查符合条件的补充解法均有双语说明与计算程序，各程序已经编译、验证，题解链接、复杂度和适用范围与实际实现一致。
- 核对复杂度参数已有定义，位数与数值上界的关系及边界正确，推导、公式和中英文说明使用一致的符号。
- 对照图例清单核查重绘图片已嵌入对应 Markdown，实际渲染查看并核对几何、数值、图注和替代文本；检查中英文资源引用无缺失或错链。
- 编译并运行参考程序；检查样例及手工设计的边界用例。
- 对适合的小规模问题，用暴力程序或独立实现随机对拍；记录规模、轮次、种子及结果。无法对拍时，写明替代验证方法。
- 如有特殊评测，单独检查接受与拒绝的典型输出。
- 确认生成的数据满足新版约束；在记录完毕的参考环境中测量标准程序，填写预估时间限制。部署到 OJ 时在目标环境重新校准正式时限。

### 5. 复核与收尾

- 对照单题记录，核实本次改动、验证结果及尚存风险。
- 在仅供内部使用的记录中保留原版与新版的对应关系；翻新成果不覆盖原仓库文件。
- 按五类状态判定当前题目，并写明缺失项、检验结果或未修复问题。
- 满足下方检验条件后，才标为“经检验通过”。

## 暂定检验通过条件

1. 新版题面可独立阅读，输入输出与样例无歧义。
2. 至少一份参考程序与题面一致，并有可阅读的解法说明。
3. 关键边界与易错情形已验证，验证方法及结果有记录。
4. 数据、生成方式和评测方式可以复现。
5. 对原版的实质改动以及仍存在的疑点已记录。
6. 中英两版题面与题解齐全、内容一致；新版公开材料已完成名称与背景检查。
7. 更改原解法时，双语题解已保留出题人解法并说明各方案的优势与代价，或明确只是另一种解法；因根本性错误不予保留时，已给出错误依据。署名准确，公开文字不包含无须发布的任务过程说明。
8. 已记录补充解法的检查结论；发现的更好、更优雅或同等优秀但思路显著不同的有效方案，均已补齐双语题解、可运行程序与验证证据。

若仍有未解决的依赖或发现错误，不标为“经检验通过”；按[状态判定顺序](题目状态分类.md)选择其他分类，并在单题记录中说明原因。

## 试运行与修订

每轮任务按用户指定的总数和批次规模推进；一批完成验收后自动开始下一批，达到约定总数后结束。只有达到分类 2“经检验通过”的独立原题计入完成数；待核实、未通过和已有衍生题不计入。每题须完成全部验证，不因批次调整而省略双语复核、图例检查或性能测量。任务数量、批次进度与续跑位置记录在内部 `review/` 中。

优先选取能够核实完整题意的正式题目。材料冲突、关键题面缺失或需要重新确定规则的候选题先记入内部待处理清单，并用其他可继续处理的题目补足批次。每批结束时记录已修复问题及流程缺口，按实际工作量调整后续规模。

## 待讨论的规则

1. **最终用途**：主要用于个人归档、公开阅读，还是投放到指定 OJ？这决定题面格式、测试包和评测环境。
2. **改动边界**：哪些题只做文字修订，哪些允许修改题意、约束或标准算法？修改后如何命名或标版本？
3. **双语格式**：四份 Markdown 文件如何命名、使用哪些固定章节、怎样统一术语和数学记号？是否仍需导出 DOCX / ODT？
4. **数据策略**：测试数据是否纳入 Git；若不纳入，怎样保证可再生成与可审核？
5. **验收强度**：对拍、独立题解、人工复核和性能测试，哪些是每题必做，哪些按题目情况选做？
6. **发布标准**：支持哪些提交语言、如何设定语言差异、内存限制和题目包格式？时间倍率及取整粒度见性能方案中的待定项。
7. **主题分类**：主题按算法、数据结构、建模方式还是其他维度划分？跨主题题目是否设次级标签？
8. **替换边界**：真实历史与政治内容具体覆盖到什么程度？如何检查新版文件名、素材、代码注释和内部记录，避免把原题中的敏感名称带进对外成果？
9. **背景风格**：故事的篇幅、人物代称、虚构世界设定和纯数学题的无故事例外，采用什么标准？

以上问题在试运行前先确定最低限度的答案，其余依据试运行结果调整。
